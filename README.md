# sigma-sap-audit-rules

Detection rules for the **SAP NetWeaver Security Audit Log**, written in Sigma, with a
log simulator and a test harness so the rules can be demonstrated without access to a SAP
system.

> **This is a personal project.** It is not affiliated with, endorsed by, or submitted to
> SAP or to the SigmaHQ project. All log data in this repository is synthetic and
> generated by `tools/sap_log_simulator.py`.

---

## Why this exists

The SAP Security Audit Log is the one place in an ERP estate where user activity is
recorded in a form an auditor or a SIEM can consume. SAP documents the following as
recordable event classes:

- successful and unsuccessful **dialog logon** attempts
- successful and unsuccessful **RFC logon** attempts
- **RFC calls to function modules**
- successful and unsuccessful **transaction starts**
- successful and unsuccessful **report starts**
- **changes to user master records**
- **changes to the audit configuration**
- activation/deactivation of **HTTP security session management**
- **file downloads** and file-system access
- **ICF recorder** entries and administration changes
- unsuccessful **password checks**

Configuration is in `SM19` / `RSAU_CONFIG`, the log is read in `SM20`, and the event
long texts are described in `SE92`.

In an intrusion-detection or GRC context, this log is usually the highest-value telemetry
the platform produces — and the least exploited. Two operational properties make it more
important than it first appears:

**1. It lives on the file system, not in the database.** The audit trail is written under
`rsau/local/file`, by default `/usr/sap/<SID>/DVEHOSTS/log/audit_<instance>`. That keeps it
off the performance path, but it also means anyone with OS access to the application server
can read, truncate or delete it. The integrity protection format (`rsau/integrity`) exists
precisely because of this.

**2. The default size limit is 1 MB.** `rsau/max_diskspace_local` defaults to
`1,000,000 bytes`. An attacker who can generate audit events quickly — a log-flood or a
noisy integration loop — can push legitimate events out of the file before they are
collected. Rotation is silent and is not itself an auditable event.

Together these make "monitoring the monitoring" a real control rather than a slogan: if an
intruder needs to operate quietly, the audit configuration is the first thing they touch.

## What is in here

```
sigma/rules/sap/         6 Sigma rules
tools/sap_log_simulator.py   generates synthetic audit events (seeded, reproducible)
tools/run_detections.py      evaluates the rules against JSONL events
tests/test_rules.py          schema checks, true positives, false-positive assertions
```

| Rule | Level | What it catches |
|---|---|---|
| `sap_audit_audit_configuration_change` | high | Audit filter changes, and `SM19` / `RSAU_CONFIG` / `SM18` being run at all |
| `sap_audit_direct_table_access_se16n` | high | `SE16N`, which reaches any table outside the role model |
| `sap_audit_user_master_change` | medium | `SU01` user master maintenance |
| `sap_audit_role_administration_pfcg` | medium | Role and role-assignment changes |
| `sap_audit_rfc_function_module_call` | medium | Remote function module execution over RFC |
| `sap_audit_logon_failure_burst` | medium | Repeated unsuccessful logons for one account |

Every rule is tagged with MITRE ATT&CK technique identifiers where a defensible mapping
exists. Where one does not, the rule says so rather than inventing a mapping.

## The normalised event schema

SAP audit log files are semi-structured text whose exact layout varies by release and by
active filter configuration. The rules therefore target a **normalised JSON schema**, which
is the contract between whatever normalises the raw file (Filebeat, Logstash, Vector) and
the rules themselves.

| Field | Type | Notes |
|---|---|---|
| `timestamp` | string | ISO-8601 UTC |
| `sap_system` | string | SID |
| `sap_instance` | string | Instance number, e.g. `00` |
| `sap_client` | string | Client, e.g. `100` |
| `event_type` | string | One of the documented event classes (below) |
| `user` | string | SAP user name |
| `client_host` | string | IP or hostname of the client |
| `terminal` | string | e.g. `SAPGUI_01` |
| `tcode` | string\|null | Transaction code, for transaction events |
| `status` | string | `SUCCESS` / `FAIL` |
| `rfc_dest` | string\|null | RFC destination (SM59) |
| `rfc_function` | string\|null | Remote-enabled function module |
| `object_name` | string\|null | Changed role, user, or path |

Permitted `event_type` values — these mirror the event classes SAP documents, so the
normaliser's vocabulary is constrained by the source system rather than invented here:

```
logon_success          logon_failure           rfc_logon_success
rfc_logon_failure      rfc_function_module_call transaction_start
transaction_end        report_start            user_master_change
role_change            role_assignment         audit_config_change
http_session_mgmt_change                      file_download
```

Mapping a real system onto this schema is the part that requires a live system and is
deliberately **not** implemented here. Numeric audit event IDs (`SE92`) are per-system and
are not hard-coded in the rules for that reason — the rules target the semantic
`event_type`, and the normaliser is responsible for the translation.

## Running it

Requires Python 3.9+ and PyYAML.

```bash
# 1. generate a synthetic day of audit events, with six attack scenarios planted in it
python3 tools/sap_log_simulator.py --seed 42 --events 400 > sample_logs.jsonl

# 2. run the ruleset
python3 tools/run_detections.py --rules sigma/rules/sap --logs sample_logs.jsonl

# 3. run the test suite
python3 -m pytest -q
```

The simulator seeds one scenario per rule, so a single run demonstrates that every rule
fires, and the test suite asserts that the two high-severity rules produce **zero** matches
against benign traffic.

## Sigma subset

`sigma-cli` was not usable in the environment this was built in, so
`tools/run_detections.py` implements only the Sigma features these rules actually use:

- selections as mappings of conditions
- equality, value lists, glob wildcards
- `|contains`, `|startswith`, `|endswith`, `|re` value modifiers
- keyword lists
- `condition` with `and`, `or`, `not`, parentheses
- `count() by <field> > <n>` aggregation

**Not implemented**, and not needed by the current rules: aggregation modifiers
(`first`, `last`, `distinct`), `near`/`re` value modifiers, `timeframe` windows.

The runner is a demonstration and test harness, not a production SIEM engine. In a real
deployment these rules would be compiled with the standard tooling.

## Design notes

**Two rules alert, four correlate.** The high-severity rules (`SE16N`, audit configuration)
are specific enough to be alerting rules on their own. The medium rules fire on routine
activity — a role change is not an incident — and exist to isolate events so that a
correlation layer can attach user, source host and time context. The test suite asserts
this distinction deliberately, so it cannot silently regress.

**Severity reflects specificity, not paranoia.** Nothing here is `critical`. A detection
that would page someone has to survive being interrogated by an analyst who knows what
normal looks like, and none of these rules do that alone.

**Known gaps.** No SoD ruleset (it is a commercial product space), no RFC destination
inventory from `SM59` to judge whether a given RFC call was expected, no handling of the
audit-log truncation described above, and no rules for `SE16`, `SM59`, `SE38`/`SA38`, or
`SE10`, which are on the natural next list. Custom wrapper transactions (`ZME23` calling
`ME23N`) bypass transaction-level checks entirely and are invisible to a tcode-based rule.
